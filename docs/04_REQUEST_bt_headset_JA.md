# speech-intake 依頼文 v0.4：Bluetooth ヘッドセット（AirPods）の入力と機器の診断（段11）

対象リポジトリ：speech-intake（段1〜10 完了の続き）
前提：`docs/REPORT_段10.md`、`intake/capture/mic.py`、`config/live.yaml`
※ すでに AirPods 対応を依頼済みの場合は、この文書のうち未実施の部分だけを行い、重なる部分は REPORT で対応関係を書く。

## 0. 位置づけ

- AirPods を Windows PC に Bluetooth アダプタでつなぎ、**マイク入力とイヤホン出力だけ**を使う（顎のモーションは使わない）。speech-intake から見れば普通の Bluetooth ヘッドセット。
- マイクを使う間、Bluetooth は通話用の接続（HFP）になり、帯域が **16 kHz（広帯域・mSBC）か 8 kHz（狭帯域）** のどちらかになる。どちらになるかはアダプタ・ドライバ・Windows の版・ヘッドセットの組み合わせで決まり、Windows の画面からは分かりにくい。
- そこで、**実際に録って確かめる診断**を足す。アダプタを買い替える判断もこの診断で行う。

## 1. ゴール

`python -m intake devcheck` を実行すると、選んだ入力機器で数秒録音し、その音が広帯域か狭帯域かを画面で見て判断できる。AirPods を入力にして `record` と `live.yaml` が動き、PC のマイクで録った同じ発話と閲覧画面で並べて比べられる。

## 2. やらないこと

- 再生側（turn-bench の仕事。別依頼）
- 顎のモーション、Apple の API
- Bluetooth のペアリングやドライバの自動操作（手順を README に書くだけ）
- エコーキャンセル

## 3. 追加するもの

### 3.1 入力機器の指定を確かにする
- `devices` の一覧に、機器名・ホスト API（MME / WASAPI など）・既定のサンプルレート・チャンネル数を出す。同じ AirPods が複数行（Stereo / Hands-Free、API ごと）に出るので、**どれがマイクとして使える行か**が分かる印を付ける
- 設定 `capture.device` は番号だけでなく**名前の一部**でも指定できるようにする（番号は抜き差しで変わるため）。複数当たったら候補を出して止まる
- 機器のサンプルレートが 16 kHz でないとき（8 kHz、44.1/48 kHz など）は 16 kHz に変換して保存し、**元のレートを `session.json` に記録**する
- 録音中に機器が消えた（電池切れ・接続切れ）ときは、それまでの録音を保存して分かるメッセージで終わる

### 3.2 診断 `python -m intake devcheck [--device 名前] [--seconds 8]`
- 指定の機器で録音し、次を `sessions/<session>/devcheck.json` と閲覧画面に出す：
  - 機器が申告するサンプルレートと、**実際の音の帯域**（4 kHz より上にどれだけ成分があるか）。機器が 16 kHz と申告していても中身が 8 kHz 相当のことがあるため、中身で見る
  - 録音の頭の欠け（マイクを開いた直後に接続が切り替わる間の無音）の長さ
  - 無音時の雑音の大きさ、音の途切れ（欠落）の有無
- 「s」「sh」「th」を含む短い英文を読むよう画面に出す（高い成分が出る音。例は README に置く）
- 判定の文言は「広帯域らしい／狭帯域らしい／判断しにくい」の 3 つまで。数値の閾値で合否にしない。**スペクトログラムを見て人が決める**

### 3.3 閲覧画面
- 波形の下に**スペクトログラム**の表示を足す（切り替え）。0〜8 kHz、4 kHz に目安の線
- 2 つのセッション（AirPods と PC のマイク）を上下に並べる比較は既存の仕組みを使う。文字起こしと単語の `p` も並ぶので、帯域の違いが STT にどう効くかを同じ画面で見られる

### 3.4 遅れの実測
- Bluetooth の入力は遅れが乗る。`speech_start` の `t_unix` がどれだけ遅れるかを知るため、**PC のマイクと AirPods で同時に同じ音（手を叩く）を録る小さな道具** `tools/latency_pair.py` を足し、2 つの波形のずれを閲覧画面で見られるようにする
- 分かった遅れは設定 `capture.latency_ms` に書けるようにし、`t_unix` の補正に使う（既定 0）

### 3.5 文書
- `README` に「Bluetooth ヘッドセットを使う」節：Windows でのペアリング、Stereo と Hands-Free の違い、`devices` → `devcheck` → `record` の順、狭帯域だったときに試すこと（Windows の更新、アダプタのドライバ、別のアダプタ）
- `docs/INTEGRATION_JA.md` §5 に、Bluetooth 入力のときの注意（遅れ、頭の欠け、モノラル）を追記

## 4. 到達点（段11）

AirPods を入力にして `devcheck` を実行すると、スペクトログラムで帯域が見える。`-c config/live.yaml record` で `speech_start` → `utterance` が届く。PC のマイクとの比較が閲覧画面に並ぶ。

## 5. 進め方の約束

- 任された範囲は確認を待たずに進め、`docs/REPORT_段11.md` で報告する。**実機（AirPods とアダプタ）が要る確認はユーザーが行う**ので、REPORT の先頭に「ユーザーが試す手順」を書く
- クラウド側では実機が無いので、8 kHz 相当・16 kHz 相当の合成音声で診断の表示を確かめる
- 1 時間を超えそうな処理は、見込みの時間と目的を先に `docs/LOG.md` に書く
- 待ち受けは localhost のみ。テストは軽く（名前での機器指定、レート変換、帯域の見積もりの合成例）
